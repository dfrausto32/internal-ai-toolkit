The bottleneck moved — design around the right one

Phase 3 optimized for a scarce GPU. Phase 5's dominant path is Claude API calls, so the scarce resource is now global.

PathBound byParallelizes?
Ollama generationGPU — one RTX 4080, ~9 GB for qwen2.5-coder:14bNo — serial on one card
Claude API (generate / review)API rate limit + cost budgetYes — async fan-out
Consequence
The limiter is the Claude rate limit (RPM + TPM) and the cost budget — both global. The GPU is demoted to a niche concern. Every decision below follows from: the scarce resource is global API budget, not compute.

The core rule: many planners, ONE scheduler

"Multiple orchestrators" is a planning concept — not multiple execution engines.

⚠ The trap
N independent orchestrators, each fanning out its own workers, against a global budget → rate-limit storms (429 thrash), no global cost ceiling, and file/test-dir collisions between unrelated projects.

The scheduler you build for one project is the same one that serves many — it just accepts work from several planners and interleaves all nodes under a single budget.

Why the reviewer can't be dropped
In Phase 3 the tests were hand-written ground truth. In Phase 5 the tester generates the tests and the worker generates the code, and they loop. Two self-generated artifacts can converge on green tests that encode the same misreading of the spec. The reviewer — which sees the original spec, not the generated tests — is what makes self-generated tests trustworthy. It stays a hard gate.

The scheduler: a bounded-concurrency DAG executor

Batch mode and multi-file mode are the same mechanism — one is just a DAG with no edges.

build DAG from each planner's nodes → compute in-degrees
ready_set = nodes with in-degree 0
worker pool (size = API concurrency bound):
    acquire API lease → run node → release lease
    on success:
        store node result (incl. its public interface)
        decrement in-degree of dependents
        newly-zero nodes → ready_set
    on hard failure:
        apply failure policy  (pluggable — see Open decisions)
repeat until DAG drained

Batch case

"Multiple independent specs" = a DAG with no edges. Every node ready at once → all pipeline up to the bound.

Multi-file case

Same scheduler with dependency edges. Modules generate in topological order; dependents wait for their inputs.

Concurrency control — two leases, not one

API lease

Bound = API rate limit (RPM and TPM). Acquired by every Claude call — generation and review alike. Must be token-aware: a burst of large-context reviews can blow TPM at low request concurrency. Retry-on-429 with backoff lives inside the lease, so a rate-limit hit pauses one worker without crashing the DAG.

GPU lease

Bound = 1 for the 14b model — only relevant if an Ollama node exists. On one 4080, two coder jobs don't run faster in parallel; they thrash VRAM. Demoted to niche: Ollama is not the dominant Phase 5 path.

Execution substrate

What actually runs a node — a direct async API call, or a spawned Claude Code agent?

✓ Recommendation
Python scheduler spine + pluggable executors. Default every node to a direct async Anthropic API call; escalate to a spawned Claude Code agent only for reasoning-heavy nodes (the planner, occasionally a gnarly worker).

Why not make nested Claude Code agents the backbone: each spawned agent starts cold, re-derives context, and — critically — has no global view of the shared rate-limit / cost budget, the exact resource Phase 5 is constrained by. The agent layer is excellent for individual judgment-heavy steps but a poor scheduler: it can't enforce a global ceiling.

The principle
Python owns scheduling and the budget. Agents / API calls are the muscle. The API-vs-agent choice is made per node, not globally — upgrade just the planner where the extra reasoning pays for itself.

The planner — a tiered component

The only node where "API call vs agent" is a real contest. It resolves by splitting the planner in two and making just one half pluggable.

Understand

What already exists, the conventions, where new code plugs in. This is the only half the substrate debate touches.

Decide

Always a structured API call — emit the module list + dependency edges as a machine-checkable DAG.
The clean seam
Both paths emit the identical validated DAG, so the scheduler never knows which produced it. Greenfield → near-empty context, agent buys nothing. Brownfield → grounding matters.
✓ Why fallback, not gate
Don't predict whether a repo is messy enough to need an agent — that prediction itself needs judgment. Let the cheap path run and self-report failure via a needs_exploration flag. You pay for the agent only when the cheap path admits defeat — never speculatively.
⚠ Trade-off accepted
A confidently-wrong planner can skip the hatch and emit a plausible-but-misgrounded DAG. The reviewer catches code drift downstream, but a bad decomposition slips through earlier. Mitigation if it bites (don't build until it does): validate the DAG's nodes against the real interfaces the context-gatherer already collected.

Shared-state hazards — the real implementation work

Latent in today's serial code; they break the moment execution goes concurrent.

HazardLocationFix
Tests run in a shared cwd / output path — concurrent pytest collidesgenerate.py · _run_testsPer-node sandbox dir + distinct output path

A dependent worker hallucinates its dependency's interfacenew cross-nodeResult store: each finished node publishes its real public interface; dependents' prompts built from spec + deps' interfaces
No global cost ceilingnew schedulerBudget tracked in the scheduler; queue/refuse new nodes past the ceiling
Most valuable contract
The result store is what prevents integration drift across modules — it matters more than raw speed. Coordination across agents is mostly "what flows along the dependency edges."
