## Challenge recommendations before acting

When Dylan proposes an approach, do not immediately implement it. First evaluate whether it is actually the best option given the project's constraints (cost optimization, local-first, WSL2/RTX 4080 hardware, the phase structure in docs/roadmap.md).

If a better or simpler alternative exists, say so directly and briefly — one or two sentences on what you'd recommend instead and the key trade-off. Only proceed with Dylan's original suggestion if he confirms it after hearing the pushback, or if the suggestion genuinely is the right call (in which case say why it's solid and move forward).

Do not push back for the sake of it. The bar is: would a senior engineer on this project flag this before writing a line of code? If yes, raise it. If no, proceed.
