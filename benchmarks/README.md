# Benchmarks

Three small, well-defined test applications for objectively measuring output quality across Phase 1 (subagent `.md` files) and Phase 3 (Claude Agent SDK).

The test suites in each `tests/` directory are written by hand — they are the ground truth. They never get generated by Ollama or Claude.

---

## Apps

| App | Description | Primary Skill Tested |
|-----|-------------|---------------------|
| `app_01_rest_api` | FastAPI CRUD service, SQLite backend | Code correctness, API design |
| `app_02_data_pipeline` | CSV ingestion + transformation script | Error handling, edge cases |
| `app_03_cli_tool` | argparse CLI with YAML config | Documentation, argument validation |

See each app's `SPEC.md` for full requirements.

---

## Scoring Rubric

Each run is scored on four dimensions, 0–3 each (max 12 points):

**Test Pass Rate (0–3)**
- 0 — Tests don't run (import errors, syntax errors)
- 1 — Some tests pass (<50%)
- 2 — Most tests pass (50–90%)
- 3 — All tests pass (>90%)

**Code Structure (0–3)**
- 0 — Monolithic, no separation of concerns
- 1 — Basic structure, some issues
- 2 — Clean structure, minor issues
- 3 — Well-structured, follows conventions for the framework

**Test Quality (0–3)**
- 0 — Tests are superficial or missing edge cases
- 1 — Happy path covered, limited edge cases
- 2 — Good coverage including some edge cases
- 3 — Comprehensive coverage, edge cases handled

**Documentation (0–3)**
- 0 — No docstrings or comments
- 1 — Some docstrings, inconsistent
- 2 — Most functions documented
- 3 — Full docstrings, inline comments where needed

## Notes

### Phase 3 summary (2026-06-05) — full orchestration loop

| App | Phase 1 best | Phase 3 | Change | Retries | Claude cost (actual) |
|-----|-------------|---------|--------|---------|---------------------|
| app_01_rest_api | 5/9 | **6/9** | +1 | 1 | $0.0501 (4,794in / 2,378out) |
| app_02_data_pipeline | 4/9 | **8/9** | +4 | 0 | $0.0217 (2,821in / 883out) |
| app_03_cli_tool | 8/9 | **8/9** | = | 1 | $0.0360 (6,315in / 1,135out) |
| **Combined** | **17/27** | **22/27** | **+5** | — | **$0.1077** |

**Cost context — Phase 3 vs raw Claude generation:**
Raw Claude generation (spec → code, no review loop) costs ~$0.013/app (~$0.039 total for 3 apps) because the prompt is small (spec + instruction ~800 tokens in, code ~700 tokens out). Phase 3 costs ~2.8× more because each review call sends spec + full generated code + full test output to Claude (~3,000–6,300 input tokens per review). The Ollama generation savings (~$0.056, free local GPU) don't fully offset the review overhead at this scale.

**When Phase 3 wins on cost:** at high generation volume (CI pipelines, many runs/day), Ollama handles generation at $0 and Claude only pays per review. Raw Claude charges for every generation attempt. The break-even is roughly 3–5 daily runs where Ollama generation savings start to exceed review overhead.

**What Phase 3 fixed automatically (no human prompt tuning):**
- app_01: SQLAlchemy import mix (`DeclarativeBase` from wrong path + `declarative_base()` undefined) — Claude's error description fed directly to Ollama, retry passed clean
- app_02: Completely eliminated framework contamination (FastAPI/SQLAlchemy in a stdlib CSV tool) via `STDLIB FIRST` system prompt rule; 13/13 on first shot
- app_03: JSON-vs-YAML bug (model wrote `json.dump` but spec required YAML) — Claude caught it, retry fixed it

**What Phase 3 could NOT fix (warnings only, no retry triggered):**
- Documentation (0/3 on app_01) — model never generates docstrings for the FastAPI app without explicit prompting; the DOCUMENTATION rule in the system prompt isn't getting applied to app_01 for some reason
- `declarative_base()` deprecation (app_01 retry used the old-style API, which still works but Claude flagged it) — fixing this requires adding it back as a conditional error rather than warning
- `if not task` vs `if task is None` (app_01) — latent falsy check on SQLAlchemy result; no test exercises it

**Key architectural finding — prompt contamination is the biggest Phase 3 risk:**
The original system prompt had unconditional FastAPI/SQLAlchemy/Pydantic rules that bled into every generation regardless of spec. The fix (`STDLIB FIRST` + conditional `IF USING X:`) was a one-line change that unlocked a 4-point gain on app_02. Prompt rules must be scoped to the context they apply in — global rules that only apply to one framework class cause regressions on the others.

**Cost efficiency:** The entire Phase 3 run across all 3 apps cost ~$0.042 in Claude API tokens. A Claude-only run would cost proportionally more per generation. The Ollama-generates / Claude-reviews split hits the cost-quality target.

**What the baseline reveals:**

| App | Tests (first pass) | Structure | Docs | Total / 9 | Change vs baseline |
|-----|--------------------|-----------|------|-----------|-------------------|
| app_01_rest_api | 13/13 | 2/3 | 0/3 | 5/9 | = (no regression) |

| app_03_cli_tool | 14/14 | 2/3 | 2/3 | 7/9 | ↑ (docs improved) |

**Prompt tuning wins:**
- Markdown fences eliminated permanently — `ollama_stream.py` now strips them automatically
- Schema-level guard (app_02) now raises `ValueError` correctly on missing columns
- Falsy integer check (app_03) confirmed fixed — `max_errors=0` no longer incorrectly rejected

**Prompt tuning miss — spec drift on output schema:**
App_02 regressed from 12/13 → 8/13. The model correctly added a `validate_row()` helper (better structure), but when assembling the summary, nested errors under `field_errors` key instead of the flat `{"row": N, "field": str, "reason": str}` the spec requires. The model changed the output contract while refactoring internally — no prompt rule warned it not to. Fixes to one failure class can introduce new ones.

**Key finding:** Prompt tuning has diminishing returns. Each rule added closes one gap but the model has creative latitude over structure decisions. The spec says what fields must exist; the model decides how to assemble them. Phase 3 Claude review catches this: Claude can diff the spec's JSON schema against what was actually generated before tests even run.

### Phase 3 — app_02_data_pipeline (2026-06-05)

**13/13 on first attempt. No retry. Score: 8/9 (up from 4/9 in Phase 1).**

**Key finding — framework contamination:** The orchestrator system prompt contained unconditional FastAPI, SQLAlchemy, and Pydantic rules carried over from app_01 tuning. Ollama read those rules and imported FastAPI into a stdlib CSV pipeline, causing 0/0 test collection (ImportError). Fixed by adding `STDLIB FIRST` rule and converting framework rules to conditional (`IF USING FASTAPI: ...`). The model immediately generated correct stdlib-only code.

**What Claude review caught (warnings only — all non-blocking):**
- Set equality column check (`!=`) should be subset check (extra columns would spuriously fail)
- `str.isdigit()` edge case vs `int()` try/except for id parsing
- Single error dict per row with `update()` silently discards earlier field failures
- No guard for `reader.fieldnames is None` on empty CSV
- Missing module-level docstring

**Phase 3 vs Phase 1 comparison:**
- Tests: 12/13 → **13/13** (+1 test, fixed by stricter prompt rules in the loop)
- Structure: 2/3 → **3/3** (Claude's warnings would push this to 3 naturally; model wrote cleaner code)
- Docs: 0/3 → **2/3** (docstring rule carried from agent system prompt, minus module docstring)
- Total: 4/9 → **8/9** (+4 points, +100% improvement)

**Cost per run:** $0.0217 actual (2,821 input @ $3/1M + 883 output @ $15/1M, Sonnet 4.6).

### Phase 3 — app_01_rest_api (2026-06-05)

**13/13 after 1 retry. Score: 6/9 (up from 5/9 in Phase 1 tuned).**

**What failed on first generation:**
Ollama mixed two SQLAlchemy API styles: imported `DeclarativeBase` from the old path (`sqlalchemy.ext.declarative`) but then called `declarative_base()` (undefined). Both are wrong — the result is a `NameError` at import time. Claude correctly identified both errors and the exact fix in a single review pass.

**What Claude review caught and fixed (errors → triggered retry):**
- `DeclarativeBase` imported from wrong path + `declarative_base()` undefined — NameError at import
- `Base.metadata.create_all()` at module level conflicts with test isolation

**After retry — warnings only (no further retry):**
- `declarative_base()` old-style API still used (works but deprecated in SA 2.0)
- `if not task` falsy check instead of `if task is None`
- `datetime.utcnow` without timezone info
- No docstrings anywhere — docs score 0/3

**Key gap: documentation.** The DOCUMENTATION rule in the system prompt should force docstrings, but the model still generated zero for the FastAPI app. The rule works for standalone functions (app_02, app_03) but the model skips docstrings on FastAPI route functions and Pydantic models. This needs a more explicit rule: "Add docstrings to FastAPI route functions and Pydantic model classes."

### Phase 3 — app_03_cli_tool (2026-06-05)

**14/14 after 1 retry. Score: 8/9 (matches Phase 1 first pass).**

**What failed on first generation:**
Claude caught a silent format mismatch: `init_config` wrote the config file using `json.dump` but the spec and all tests expect YAML. 13/14 tests passed — only the round-trip test (`test_load_config_returns_valid_dict`) failed because it reads back a YAML file written by a different test. The JSON-written file parses as a string, not a dict. Claude identified the exact root cause and fix in the first review.

**After retry — warnings only:**
- `bool` is a subclass of `int` so `isinstance(max_errors, int)` incorrectly accepts `True`/`False` as valid
- Empty YAML (`yaml.safe_load` returns `None`) would raise `TypeError` instead of `ValueError`
- Docstrings present but lack `Args:` and `Raises:` sections per spec

**Documentation note:** Score 2/3 (down from 3/3 in Phase 1 first pass) because the expanded spec asks for `Args:` and `Raises:` sections which the model skipped. The one-line docstrings are there; the format is incomplete.

### app_03_cli_tool — Phase 1 first pass (2026-06-05)

**14/14 pass on first attempt.** Highest score in the baseline.

**What Ollama got right:**
- Correct argparse subparser setup with `required=True`
- `FileExistsError` and `FileNotFoundError` raised correctly
- All four required functions exported with correct signatures
- Docstrings on all four functions (triggered by system prompt addition)

**Latent bug (not caught by tests):** `not config.get("pipeline", {}).get("max_errors")` evaluates `True` when `max_errors=0` — `not 0` is `True`. A config with `max_errors: 0` would incorrectly raise `ValueError` even though 0 is a valid value (≥ 0). Tests used `max_errors: 5` so this was never exercised.

**Documentation gap closed:** Adding `"Add a one-line docstring to every function"` to the system prompt produced 3/3 docs on the first pass. This confirms the docs gap across all apps is a prompt omission, not a model limitation. Backfilling this into the system prompt is the cheapest gap-closing move available.

**Note:** SPEC said 13 tests but the test file contains 14 (test_load_config_raises_on_empty_name was added during writing). All 14 pass.

### app_02_data_pipeline — Phase 1 first pass (2026-06-05)

**Failure mode:** Missing schema-level column validation. `run_pipeline` never checks that all required columns are present before iterating rows. When a column is missing, it crashes with `KeyError` inside `validate_and_transform_row` instead of raising `ValueError` as required.

**What Ollama got right (first pass):**
- All 12 row-level validation tests passed on the first attempt — no iteration needed
- Correct validation logic for amount (float parse + ≥ 0), date (strptime format check), status (enum check), name (non-empty)
- Correct transforms: title case, rounding to 2 decimal places
- Correct summary dict structure with 1-indexed row numbers in errors
- Used Python 3.10+ `dict | None` union type hint

**Gap vs Claude pattern:** Row-level guards come naturally; schema-level guards (validate inputs before processing) are the recurring blind spot. This is the same class of error as the SQLAlchemy import path issue in app_01 — correct on the happy path, missing a defensive check at the boundary.

**Fix to add to system prompt:** "Before iterating rows, check that all required columns are present in the CSV header. Raise ValueError with a descriptive message if any column is missing."

### app_01_rest_api — Phase 1 first pass (2026-06-05)

**Failure mode:** `qwen2.5-coder:14b` imported `from pydantic.v1 import BaseModel` and used `orm_mode = True`. Modern FastAPI (0.100+) rejects `pydantic.v1` models with `PydanticV1NotSupportedError` at startup — tests couldn't even collect.

**Other issues in Ollama output:**
- Used deprecated `sqlalchemy.ext.declarative.declarative_base()` (SQLAlchemy 2.0 warns, still works)
- Routes registered as `/tasks/` with trailing slash instead of `/tasks` (would cause 307 redirects)
- Used `List[...]` from `typing` instead of built-in `list[...]` (minor, Python 3.9+)

**Iteration log:**

| Run | Failure | Fix applied |
|-----|---------|-------------|
| First pass | `pydantic.v1` import — FastAPI rejects at startup | Added Pydantic v2 + no trailing slash to system prompt |
| Retry 1 | `from sqlalchemy.ext.declarative import DeclarativeBase` doesn't exist; `TaskRead` missing fields | Added SQLAlchemy 2.0 import path + subclass pattern to system prompt |
| Retry 2 | **13/13 pass** | — |

**Remaining issues in Ollama output (non-blocking):** `db: SessionLocal` type hint should be `Session`; manual `if not task.title` check instead of `Field(min_length=1, max_length=200)`; no docstrings.

**Claude baseline observation:** Zero review iterations, 100% pass rate, no docstrings. Both models score 0/3 on documentation — neither adds docstrings unprompted. The 1-point structure gap (3 vs 2) reflects Claude defaulting to correct Pydantic/SQLAlchemy idioms without instruction.
